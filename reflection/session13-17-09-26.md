## Notes

### 1. Modular Architecture & Parallel Workflows

* **Separation into Distinct Packages:**
    * Dividing the codebase into independent layers (such as domain models, builders, layout engines, and views) creates clear ownership boundaries.
    * Clear package boundaries allow multiple team members to implement features simultaneously (e.g., core tree algorithms vs. visual UI elements) without modifying the same source files.
* **Minimizing Merge Collisions:**
    * Early architectural planning and decoupled code structures drastically reduce Git merge conflicts during concurrent development.

> **Extended Technical Context:**
> * **Interface-Based Contracts:** Defining strict API contracts and interfaces before implementation allows team members to mock dependent layers, unblocking downstream UI development while core algorithms are still being finalized.
> * **Single Responsibility Principle (SRP):** Isolating layout math, state models, and canvas rendering into separate packages prevents cascading regressions when internal algorithms are refactored.

---

### 2. Build Tooling & Environment Standardization (Maven)

* **Centralized Dependency Management:**
    * Relying on build automation tools like Maven eliminates manual `.jar` linking and classpath mismatches across different development machines.
    * Declaring explicit versions (such as JavaFX runtime modules) inside `pom.xml` ensures that build behaviors remain reproducible across all workstations.
* **Eliminating "Works on My Machine" Inconsistencies:**
    * Automated dependency resolution guarantees that compilation, testing, and packaging execute under identical configurations for every developer.

> **Extended Technical Context:**
> * **Lifecycle Phases & Plugins:** Maven enforces standard lifecycle phases (`compile`, `test`, `package`) paired with plugins (like `javafx-maven-plugin`) to bundle platform-specific native binaries and modular VM options automatically.
> * **Transitive Dependency Resolution:** Declarative build descriptors prevent version drift by automatically resolving shared indirect dependencies and detecting library version conflicts before runtime.

### 3. Subsystem Wiring: Connecting Backend Logic to GUI

* **Bridging Inputs to Domain Models:**
    * Integrating distinct modules requires cleanly routing user actions from control inputs (e.g., text fields, buttons) to trigger internal data structure operations.
    * Inputs must be validated and sanitized at the boundary before calling model operations to prevent unexpected runtime state errors.
* **Component Communication:**
    * Rather than tightly coupling views to models, UI components notify backend controllers of user actions, which in turn update state and trigger canvas re-renders.

> **Extended Technical Context:**
> * **Observer / Event-Driven Wiring:** Utilizing listener patterns or observable properties allows the UI view to automatically react whenever the underlying data structure mutates, eliminating manual polling or bidirectional object coupling.
> * **Boundary Validation:** Enforcing strict input parsing (e.g., rejecting non-integer values or duplicate keys prior to invoking tree insert routines) guarantees that algorithmic invariants are never corrupted by malformed GUI inputs.
