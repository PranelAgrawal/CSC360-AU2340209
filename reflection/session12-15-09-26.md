## Notes

### 1. Tree Layout Computation & Coordinate Mapping

* **Translating Hierarchy to 2D Space:**
    * Converting a logical tree (nodes and pointers) into visual elements requires calculating precise `(x, y)` coordinates for each node before drawing.
    * In a standard layout, the vertical position (`y`) is directly tied to the node's depth level, while horizontal spacing (`x`) must adapt dynamically.
* **Handling Sibling Overlap:**
    * As tree depth increases, the number of potential nodes doubles at each level, causing visual crowding.
    * Subtree widths must shrink or adjust recursively based on level depth so that left and right branches do not intersect or obscure one another.

> **Extended Technical Context:**
> * **Recursive Space Allocation:** Standard algorithms (like Reingold-Tilford) compute subtree bounding boxes from the bottom up (post-order traversal), ensuring subtrees are spaced just far enough apart to eliminate collisions while keeping parent nodes centered over their immediate children.
> * **Time Complexity of Layout Passes:** Pre-computing coordinates takes linear time, $O(N)$ for $N$ nodes, keeping the UI responsive without needing heavy recalculations per frame unless the tree topology changes.

### 2. Decoupling Data Structures from Visual Views

* **Model vs. View Separation:**
    * Logical components (`Node`, `BinarySearchTree`) should never hold direct references to visual UI elements like colors, coordinates, or canvas shapes.
    * The rendering layer reads the tree structure purely to produce visual shapes, leaving the core data structure independent and testable without launching a GUI.
* **Maintenance Benefits:**
    * Isolating domain logic allows modifying tree operations (e.g., rebalancing, insertion) without risking bugs in the rendering pipeline, and vice versa.

> **Extended Technical Context:**
> * **Design Pattern Application:** This cleanly follows the Model-View-Controller (MVC) or Model-View-Presenter (MVP) architecture. The model stores data integrity and traversal rules, while dedicated renderer components interpret state snapshots into UI primitives.
> * **Headless Testing:** Decoupled data models can be thoroughly verified through automated unit tests in terminal or continuous integration environments without requiring display drivers or GUI framework initializations.

### 3. Canvas Interaction: Pan, Zoom, and Boundary Clipping

* **Interactive Navigation:**
    * Larger trees quickly exceed screen dimensions, requiring interactive controls like drag-to-pan and mouse-wheel zoom to inspect specific subtrees.
    * Transformations are applied directly to the rendering context rather than manually mutating individual node coordinates.
* **Viewport Clipping & Edge Cases:**
    * Drawing elements outside the active display window consumes unnecessary computing cycles and can cause rendering glitches.
    * Pruning or clipping elements that fall beyond the visible canvas bounds keeps panning and zooming smooth.

> **Extended Technical Context:**
> * **Affine Transformations:** Panning and zooming are typically handled by applying a single $3 \times 3$ transformation matrix (translation + uniform scaling) directly to the canvas context, mapping world coordinates to screen pixels in $O(1)$ computation per frame.
> * **Frustum/View Culling:** Checking whether a node's bounding box intersects the current viewport boundaries before issuing draw calls avoids redundant GPU/CPU rasterization overhead on off-screen branches.
